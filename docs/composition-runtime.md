# Композиция и применение изменений

`Composition<TNode>` связывает composable-код с деревом конкретного приложения через
`IApplier<TNode>`. Runtime не зависит от UI-фреймворка. Узлы — ссылочные типы; Applier
решает, как создавать связи между ними, изменять свойства и удалять детей.

## Два режима работы

`SetContent(content)` сразу вычисляет и применяет первоначальную композицию. При
следующих вызовах он сопоставляет новое выполнение с уже существующими группами.
Если нужен список будущих операций, используйте отдельные фазы:

```csharp
using Composition<MyNode> composition = new Composition<MyNode>(applier);
composition.ComposeContent(content);

CompositionChangeSet changes = composition.PendingChanges!;
foreach (CompositionOperation operation in changes)
    Console.WriteLine(operation);

composition.ApplyChanges(changes);
```

Между вычислением и применением дерево и основная SlotTable не изменяются. Даже
фабрики новых узлов выполняются только при применении. `DiscardChanges()` отменяет
подготовленный результат. Один набор операций можно применить один раз и только
к породившей его композиции. До применения или отмены нельзя вычислять следующий.

`Recompose()` обрабатывает изменения state и возвращает `true`, когда подготовлен
результат, требующий `ApplyChanges()`. Список операций может оказаться пустым: новое
выполнение могло изменить только зависимости от state или restart-делегаты.

## Что находится в списке операций

Операции описывают изменения групп, слотов и дерева. `GroupIndex` обозначает
логическую позицию группы или границу вставки, `NodeIndex` — позицию узла среди детей
текущего узла Applier, а `SlotOffset` — номер пользовательского слота внутри группы.
Для перемещений `SourceGroupIndex` и `SourceNodeIndex` указывают исходные позиции.
Не относящиеся к операции поля равны `null`. Позиции относятся к последовательности
в момент выполнения соответствующей операции.

Для операций Applier индекс относится к детям его текущего узла. `Down` и `Up`
изменяют текущий узел. У `MoveNode` и `MoveGroup` назначение задано в координатах
до перемещения. Например, перемещение одного элемента из 1 в 3 меняет
`[A, B, C, D]` на `[A, C, B, D]`.

Runtime вызывает оба hook вставки: `InsertTopDown` перед обработкой детей и
`InsertBottomUp` после неё. Конкретный Applier должен выполнять фактическую вставку
в подходящем ему hook. Выполнение вставки в обоих создаст дубликат.

Список предназначен для проверки и диагностики. Применением управляет композиция,
поскольку изменения SlotTable и дерева должны оставаться согласованными.

## Как сопоставляются группы

Во время исполнения Composer сравнивает следующий вызов группы с оставшимися
детьми предыдущей группы. Совпадение ключа, вида группы и пользовательского ключа
позволяет повторно использовать существующую группу, её слоты и узлы.

При изменении порядка Composer использует ключи из Reader. Повторяющиеся ключи
сопоставляются в порядке их старых вхождений. Для списков, в которых состояние
должно следовать за элементом, используйте `StartMovableGroup(key, dataKey)` либо
composable-помощник `Composables.Key`. Без пользовательского ключа одинаковые
вхождения сохраняют позиционную семантику.

Результат вычисления содержит подготовленные группы и операции. Пропущенные
группы сохраняют предыдущие данные. Новые поддеревья записываются во временную
SlotTable; при применении Writer переносит их в основную и преобразует anchors.
Перемещение существующего поддерева сохраняет его anchors.

`GroupAnchor` обозначает существующую группу конкретной таблицы и остаётся тем же
при изменении её логического индекса. Reader возвращает anchor через `Anchor(index)`.
Удаление группы делает его недействительным; anchor другой таблицы отклоняется.
Физические адреса массива нужны только внутренней реализации gap buffer и не
передаются в Reader, Writer или Composer.

Основная таблица принадлежит композиции. `SlotTable.OpenReader()` можно использовать
для диагностики; закрывайте Reader перед применением изменений. Внешнее открытие
Writer меняет версию таблицы и делает подготовленный результат недействительным.

## Автоматическая рекомпозиция

В UI-приложении передайте Recomposer существующий контекст потока приложения:

```csharp
SynchronizationContext context = SynchronizationContext.Current
    ?? throw new InvalidOperationException("Нужен контекст приложения.");
using Recomposer recomposer = new Recomposer(context);
using Composition<MyNode> composition = new Composition<MyNode>(applier, recomposer);
composition.SetContent(content);
```

Контекст должен последовательно выполнять callbacks на потоке, где созданы
Recomposer и композиции. Обычный `new SynchronizationContext()` для этого не
подходит. Один Recomposer обслуживает несколько композиций. Его освобождение
останавливает планирование; сами композиции освобождаются отдельно.

Чтения state привязываются к ближайшей restart-группе, либо к корню. Генератор
передаёт ей делегат повторного вызова через `UpdateScope`. Изменение state позволяет
повторить эту область, сохранив остальные. Пропуск родителя не мешает выполнить
изменившегося потомка. При ручном использовании restart-групп нужно также задавать
их restart-делегаты.

Изменять глобальный state можно с другого потока. Выполнение composable-кода и
работа Applier остаются на потоке владельца. Несколько уведомлений объединяются
в один запрос через `SynchronizationContext.Post`. Изменение, пришедшее во время
вычисления или применения, сохраняется для следующего прохода.

Вычисление выполняется в mutable snapshot. Отменённые snapshots не публикуют
значения; конфликт записей обнаруживается до изменения дерева. Для собственных
политик слияния значимых типов используйте `ISnapshotMutationPolicy<T>.TryMerge`:
возвращаемый `bool` отличает отказ от допустимого результата `default(T)`.

## Жизненный цикл и ошибки

Новые remembered-объекты получают `OnRemembered` после применения. Удалённые получают
`OnForgotten` в обратном порядке; созданные в отменённом вычислении — `OnAbandoned`.
`LaunchedEffect` начинает работу после применения и отменяет свой
`CancellationToken` при удалении из композиции. Для этого используются стандартные
средства .NET, без отдельного аналога CoroutineScope.

Исключение при вычислении отменяет подготовленный результат. Исключение Applier
переводит композицию в `IsFaulted`: её необходимо освободить и создать заново,
поскольку внешнее дерево могло измениться частично. Автоматические ошибки доступны
через `Recomposer.Error`; без обработчика исключение выходит из callback контекста.
Повторный `Dispose` безопасен. Неуспешный автоматический проход не запускается
бесконечно без нового события.

Рабочий консольный пример с просмотром операций находится в Playground. Перенос
содержимого между композициями, CompositionLocal, специализированная обработка
derived state и кадровый планировщик в этот этап не входят.
